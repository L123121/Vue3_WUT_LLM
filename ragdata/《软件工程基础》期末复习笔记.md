# 第一章 软件工程概述

## 1.1 软件及其特性

> **软件 = 程序（Program）+ 数据（Data）+ 文档（Document）**

### 🔥 软件的本质特性

| 特性 | 说明 |
|:---|:---|
| **复杂性（Complexity）** | 规模巨大，由许多简单部分相互关联组成 |
| **一致性（Conformity）** | 不能独立存在，需依附于环境 |
| **可变性（Changeability）** | 软件不断演变 |
| **不可见性（Invisibility）** | 逻辑实体，无法直接可视化 |

## 1.2 软件工程的基本要素

```
        ┌─────────────┐
        │   软件工程    │
        ├──────┬──────┤
        │ 质量 │ 过程 │
        ├──────┴──────┤
        │    方法      │
        ├─────────────┤
        │    工具      │
        └─────────────┘
```

## 1.3 🔥 软件工程的定义（IEEE 610.12-1990）

> ① 将**系统性**的、**规范化**的、**可定量**的方法应用于软件的**开发、运行和维护**
> ② 对①中所述方法的研究

## 1.4 软件工程的基本目标

- 较低的开发成本
- 按时完成开发并及时交付
- 实现客户要求的功能
- 具有良好的性能、可靠性、可扩展性、可移植性
- 软件维护费用低

## 1.5 软件危机

- **定义**：在计算机软件的开发和维护过程中所遇到的一系列严重问题
- **表现**：维护困难、工期拖延、成本超支、质量难保证

## 1.6 ⭐ 软件工程 vs 编程

| 编程（Programming） | 软件工程（Software Engineering） |
|:---:|:---:|
| 实现给定蓝图的手艺 | 理解业务问题并提出解决方案 |
| 实现软件工程师设计的软件 | 设计软件的"蓝图" |
| 关注编码实现 | 关注全生命周期 |

## 1.7 🔥 软件工程七大基本原理

1. **用分阶段的生命周期计划严格管理**
2. **坚持进行阶段评审**
3. 实行严格的产品控制（防止随意变更）
4. 采用现代程序设计技术
5. 结果应能清楚地审查
6. 开发小组的人员应少而精
7. 不断改进软件工程实践的必要性

# 第二章 软件过程

## 2.1 软件工程过程

```
问题定义 → 需求开发 → 软件设计 → 软件构造 → 软件测试 → 软件维护
```

### ⭐ 验证 vs 确认

- **验证（Verification）**：Did we build the system **right**?（正确构建？）
- **确认（Validation）**：Did we build the **right** system?（构建正确？）

### 晚修正的成本

```
需求阶段修正成本：  1倍
设计阶段修正成本：  3倍
实现阶段修正成本：  7倍
测试阶段修正成本：  12倍
维护阶段修正成本：  50-200倍
```
> ⚠️ **越早发现缺陷，修正成本越低！**

## 2.2 🔥 常见软件过程模型

### （1）瀑布模型（Waterfall Model）

```
需求定义与分析 → 软件设计 → 软件实现 → 软件测试 → 运行与维护
```

| 方面 | 内容 |
|:---|:---|
| **特点** | 以**预测性**为原则，以**文档驱动**，以过程控制为核心 |
| **优点** | 阶段划分固定，里程碑明确 |
| **缺点** | 难以响应用户变更；早期错误后期才能发现；产生大量文档 |
| **适用** | 需求在初期可完整确定，用户环境稳定 |

### （2）原型模型（Prototyping）

```
需求定义与分析 → 快速原型化 → 确认验证 → 设计/实现/测试/维护
```

- 快速建造可运行原型，适合需求模糊场景

### （3）演化模型

- **增量模型**：每次发布逐步增加功能，直至全部功能
- **迭代模型**：一开始提交完整系统，后续补充完善各子系统

### （4）⭐ 统一过程模型（RUP）

- 迭代增量式开发，适合现代大型项目

### （5）🔥 敏捷开发（Agile）

#### 敏捷宣言四大价值观
1. **个体和互动**高于流程和工具
2. **可工作的软件**高于详尽的文档
3. **客户合作**高于合同谈判
4. **响应变化**高于遵循计划

#### TDD（测试驱动开发）

```
红（Red）→ 写一个失败测试
绿（Green）→ 写刚好能让测试通过的代码
重构（Refactor）→ 优化代码并重新测试
```

#### 常见敏捷方法：极限编程（XP）、Scrum

# 第三章 需求获取

## 3.1 ⭐ 需求的定义

- **Jackson模型**：需求描述的内容包括——**机器领域（Machine Domain）**、**应用领域（Application Domain）**、**shared phenomena（共享现象）**
- shared phenomena = 机器能感知的现实事件 + 机器能触发的现实行为

## 3.2 🔥 需求的分类

### 按性质分

| 类型 | 定义 | 示例 |
|:---|:---|:---|
| **功能性需求** | 系统做什么（功能） | 电梯将人送到所选楼层 |
| **非功能性需求** | 做到什么程度（质量） | 电梯30秒内到达 |

### 按抽象层次分

```
业务需求 → 用户需求（客户语言） → 系统需求（开发者语言） → 软件设计规约
```

## 3.3 🔥 需求获取技术

| 技术 | 适用场景 | 特点 |
|:---|:---|:---|
| **面谈** | 真正的专家存在时 | 问问题，听答案 |
| **问卷调查** | 大基数被访者 | 统计分析科学 |
| **头脑风暴** | 需求不明确时 | 不评价、不批评、互相启发 |
| **参与观察法** | 知识无言以表时 | 分析师越被动越好 |
| **亲身实践** | 用户太忙 | 边做边学 |
| **文档分析** | 有现有系统时 | 发现可重用部分 |
| **原型法** | 需求模糊时 | 可视化，直观沟通 |
| **情景分析（Scenario）** | 需理解交互时 | 描述具体使用场景 |

## 3.4 ⭐ 需求过程

```
需求获取（Elicitation）→ 需求分析（Analysis）→ 需求规约（Specification）
→ 需求验证（Validation）→ 需求管理（Management，贯穿全过程）
```

# 🔥🔥 第四章 面向对象分析与设计（OOAD）
> **本章是应用题重点，含用例图、类图、顺序图、状态图四大建模**

## 4.1 🔥 面向对象基本概念

> **面向对象 = 对象 + 分类 + 继承 + 消息通信**

### 对象（Object）

```
对象 = 属性（数据/状态）+ 方法（行为/操作）
例：汽车对象 → 状态：颜色=蓝，速度=200mph  行为：换挡、转向、刹车
```

### 类（Class）

- 具有相同属性和方法的对象集合的**蓝图**
- **实例化（Instantiation）**：从类创建对象的过程

### 🔥 三大特性

| 特性 | 描述 |
|:---|:---|
| **封装（Encapsulation）** | 隐藏内部状态，通过接口访问 |
| **继承（Inheritance）** | 子类继承父类的属性和方法 |
| **多态（Polymorphism）** | 不同对象对同一消息做出不同响应 |

## 4.2 🔥 UML 图分类

| 视图类型 | 包含的图 |
|:---|:---|
| **结构视图** | 类图、对象图、构件图、部署图 |
| **行为视图** | 用例图、顺序图、协作图、状态图、活动图 |

### UML "4+1"视图

```
            ┌──────────┐
            │ 用例视图  │
            ├──────────┤
 逻辑视图 ──┤          ├── 实现视图
 进程视图 ──┤          ├── 部署视图
            └──────────┘
```

1. **用例视图** → 干系人需求
2. **逻辑视图** → 系统功能
3. **进程视图** → 运行特性
4. **实现视图** → 组装配置
5. **部署视图** → 拓扑分布

## 4.3 🔥🔥 用例图（Use Case Diagram）

### 组成元素

```
参与者（Actor）    ——   人/外部系统/硬件设备（关注角色，非具体个人）
用例（Use Case）   ——   有价值服务功能
关联（Association）——   交互通道
系统边界（Boundary）——   内外部界线
```

### ⭐ 参与者注意事项

- 不同用户可充当同一角色
- 同一用户可扮演不同角色

### 🔥 用例之间的关系

| 关系 | 关键字 | 说明 |
|:---|:---:|:---|
| **包含** | `<<include>>` | 基本用例执行时，被包含用例**一定执行** |
| **扩展** | `<<extend>>` | 基本用例执行时，扩展用例**可选择执行** |
| **泛化** | —▷（实线空心三角） | 一般与特殊关系 |

### 🔥 用例 vs 场景

| 用例（Use Case） | 场景（Scenario） |
|:---|:---|
| 功能的通用描述 | 用例的**实例** |
| 抽象 | 具体 |

### 📝 用例建模习题（完整模板）

> **题目**：音像商店系统。销售/租借录像带和光碟，有1000盘录像带和500张光碟。所有物品有条码，可用条码扫描仪支持销售和返还。客户会员卡也条码化。客户可预定录像带并在指定日期来取。系统必须有灵活的搜索机制来回答客户询问。

**第一步：确定参与者和系统边界**
- 系统边界：音像制品租售系统
- 参与者：**客户**、**供应商**、**店员**

**第二步：确定用例及关系**

```
客户 ──── 咨询商品
     ──── 预订录像品  ←<<extends>>── 销售录像品
     ──── 租借录像品  ←<<extends>>── 归还录像品
     ──── 归还录像品

供应商 ── 退货

店员 ──── 退货
     ──── 销售录像品
     ──── 归还录像品
     ──── 维护客户信息
```

> 关系说明：`预订录像品 <<extends>> 销售录像品` → 销售时可能扩展出预订处理；`租借录像品 <<extends>> 归还录像品` → 归还流程是租借的扩展

### 用例建模步骤
1. 找出系统外部的参与者和系统边界
2. 确定每个参与者期望的系统行为
3. 命名用例（主动语态，动词起始）
4. 绘制用例图
5. 区分包含（include）/ 扩展（extend）/ 泛化关系

## 4.4 🔥🔥 类图（Class Diagram）

### 类的表示

```
┌───────────────┐
│    类名        │
├──────┬────────┤
│ 属性 │ name   │
│      │ age    │
├──────┼────────┤
│ 操作 │ eat()  │
│      │ sleep()│
└──────┴────────┘
```

### 🔥 类之间的关系

| 关系 | 符号 | 描述 | 记忆点 |
|:---|:---:|:---|:---|
| **关联** | ———— | 类之间的连接（可有方向/角色） | 实线 |
| **聚合** | ◇——— | 整体-部分，**部分可独立**存在 | 空心菱形 + 实线 |
| **组合** | ◆——— | 整体-部分，**部分不可独立**存在 | 实心菱形 + 实线 |
| **泛化** | —▷ | 继承关系（子类继承父类） | 实线 + 空心三角 |
| **依赖** | - - -> | 一个类变化引起另一个变化 | 虚线 + 箭头 |
| **实现** | - - ▷ | 类与接口的关系 | 虚线 + 空心三角 |

### 多样性（Multiplicity）

```
0..1  — 可选的（0或1）         1..1  — 有且仅有一个
0..*  — 零或多个               1..*  — 一或多个
20..100 — 最少20，最多100
```

### 关联类

- 当关联本身也有属性时，使用**关联类**（用虚线与关联线相连）
- 例：学生选修课程，有"成绩"属性 → 可在关联线上附加关联类"选课记录"

### 📝 类图建模习题（含参考答案）

> **题目**：一个学生可以选修最多10门课程，也可能没有任何课程；一门课程可以被最多100名学生选修，一门课程选课人数少于20不能开课；一个老师可以教授多门课程或者不教课；每门课程至少有一个老师，也可以多个老师任教；每门课程可以有1或多本教材，每本教材只能用于一门课程。

## 4.5 🔥🔥 顺序图（Sequence Diagram）

### 组成元素

| 元素 | 符号 | 说明 |
|:---|:---|:---|
| **对象（Object）** | `对象名:类名` 方框（带下划线） | 参与交互的实体 |
| **生命线（Lifeline）** | 虚线垂直线 | 对象生命周期 |
| **激活期（Activation）** | 细长矩形 | 操作执行时间段 |
| **消息（Message）** | 箭头线 | 对象间交互 |

### 🔥 对象的三种形式

```
① 有对象名有类名：  对象名:类名        例 → user:User
② 仅有对象名：      对象名             例 → user
③ 🔥 匿名对象：    :类名             例 → :LoginServlet
   （没有给出对象名，冒号后直接接类名，表示匿名对象，常用于临时创建的实例）
```

### 🔥 消息类型

```
  ──►  同步消息（实心箭头）     —— 发送方等待返回（阻塞调用）
  ──▶  异步消息（线形箭头）     —— 发送方不等待（非阻塞）
  - -▶ 返回消息（虚线箭头）     —— 从被调用方返回结果
  ──►  自反消息（指向自身）     —— 对象调用自己的方法
```

> 同步 vs 异步：同步是**实心箭头**（调用方等结果），异步是**线形箭头**（发完继续执行）

### 🔥 组合框（Frame）

```
opt [条件]    ——  if（可选片段，条件为真才执行，无else）
alt           ——  if/else（分支选择，框内用水平虚线分隔多个区域）
  [条件1]       → 区域1
  [条件2]       → 区域2（else 或 elif）
loop [次数]   ——  循环
par           ——  并发执行
ref           ——  引用其他图
```

> **alt框含义**：相当于程序中的 if/else 分支结构。框内被水平虚线分隔为多个区域，每个区域对应一个条件分支，运行时根据条件满足情况执行对应区域。

### 📝 顺序图的作用
- 检查用例中描述的需求是否已落实给具体对象
- 补充遗漏的对象类或操作
- 识别主动对象

## 4.6 🔥🔥 状态图（State Diagram）

### 基本概念

- **状态（State）**：对象在某个时间段的属性取值
- **迁移（Transition）**：
  ```
  源状态 → 触发事件 [警戒条件] / 动作 → 目标状态
  ```

### 🔥🔥 起始状态与终止状态（必考重点！）

```
● 起始状态（实心圆）：
  - ✅ 必须存在，一定要有！         ← 画图第一步
  - ✅ 有且仅有一个                ← 唯一性

◎ 终止状态（实心圆外加圈）：
  - ❌ 可有可无（可以没有终止状态）
  - ✅ 可以有多个终止状态
```

> 画状态图时：**先画起始状态（一个实心圆）**，再画各个状态节点和迁移，最后根据需要决定是否添加终止状态。

### 4种事件类型

| 类型 | 说明 |
|:---|:---|
| **变更事件（Change Event）** | 给定条件成立时发生 |
| **调用事件（Call Event）** | 对象的操作被调用时发生 |
| **时间事件（Time Event）** | 时间段过去或特定时间点触发 |
| **信号事件（Signal Event）** | 对象收到实时信号 |

### 状态活动

```
entry/action    —— 进入状态时执行
exit/action     —— 退出状态时执行
do/activity     —— 状态中持续执行
```

### 组合状态

- **OR组合**：满足其中一个子状态即可
- **AND组合（并发）**：同时满足所有子状态
- **历史状态（H / H\*）**：记住退出时的子状态

# 第五章 软件体系结构

## 5.1 组成要素

```
SA = { 元素（Elements）, 形式（Form）, 准则（Rationale） }
简化：SA = 构件 + 连接件 + 约束
```

三种设计元素：
- **处理元素**（Processing Elements）
- **数据元素**（Data Elements）
- **交互元素**（Interaction Elements）

## 5.2 🔥 常见体系结构风格

| 风格 | 特点 | 适用示例 |
|:---|:---|:---|
| **管道-过滤器** | 数据流连接连续处理步骤 | 媒体播放器 |
| **事件驱动（隐式调用）** | 构件通过事件交互，松散耦合 | IDE调试器 |
| **仓库（以数据为中心）** | 共享数据存储，各构件访问同一数据 | 数据库系统 |
| **C/S（客户机/服务器）** | 分布式模型，客户端请求服务端响应 | Web应用 |
| **B/S（浏览器/服务器）** | 三层C/S实现，浏览器作为客户端 | 网页应用 |
| **MVC** | 模型-视图-控制器分离 | Web框架 |
| **P2P（对等网络）** | 每节点既是客户端也是服务器 | 文件共享 |

## 5.3 风格选择原则

- 层次化思想在任何系统都适用
- 问题可分解为连续阶段 → 管道-过滤器
- 需灵活/松散耦合 → 事件系统或C/S

## 5.4 🔥 模块独立性

### 耦合（Coupling）—— 越低越好

| 耦合类型 | 特点 | 独立性 |
|:---:|:---|:---:|
| **非直接耦合** | 两模块无直接关系 | ⭐⭐⭐⭐⭐ |
| **数据耦合** | 传递简单数据参数 | ⭐⭐⭐⭐ |
| **标记耦合** | 传递数据结构 | ⭐⭐⭐ |
| **控制耦合** | 传递控制信息控制功能 | ⭐⭐ |
| **外部耦合** | 均与同一外部环境关联 | ⭐⭐ |
| **公共耦合** | 引用同一公共数据区 | ⭐ |
| **内容耦合** | 直接访问另一模块内部 | ⭐（禁止🚫） |

### 内聚（Cohesion）—— 越高越好

| 内聚类型 | 特点 | 强度 |
|:---:|:---|:---:|
| **功能内聚** | 所有部分为完成同一功能 | ⭐⭐⭐⭐⭐ |
| **信息内聚** | 多个功能在同一数据结构上操作 | ⭐⭐⭐⭐ |
| **通信内聚** | 使用相同输入/产生相同输出 | ⭐⭐⭐ |
| **过程内聚** | 必须以特定次序执行 | ⭐⭐ |
| **时间内聚** | 所有功能在同一时间段执行 | ⭐⭐ |
| **逻辑内聚** | 逻辑相似功能组合，参数决定执行 | ⭐ |
| **巧合内聚** | 各部分之间无联系 | ⭐（避免🚫） |

> **设计目标：高内聚 + 低耦合**

# 第六章 编写高质量的代码

## 6.1 编码规范

- 软件全生命周期 **70%** 成本是维护
- 软件很少由原编写人员维护
- **目的**：提高编码质量、可读性、可重用性、可移植性

## 6.2 注释规范

- **真注释**：说明实现原因、原理和难点（解释"**为什么**"，不是"怎么做"）
- **文档字符串**：说明如何使用（Args, Returns）
- 修改代码时同步更新注释

## 6.3 命名规范

| 元素 | 规范 |
|:---|:---|
| 宏、枚举 | 全部大写 + 下划线（MAX_VALUE） |
| 变量、文件 | 全部小写 + 下划线（user_name） |
| 函数、类型 | 大小写混写（MyClass） |
| 常量 | k开头（kMaxCount） |

## 6.4 语句构造原则

1. 不要为了节省空间把多个语句写在同一行
2. 先考虑清晰性，不要刻意追求技巧性
3. 程序要简单清楚，直截了当
4. 尽量避免复杂的条件测试
5. 减少对"非"条件的测试
6. 避免大量使用循环嵌套和条件嵌套
7. 利用括号使运算次序清晰直观

# 🔥🔥🔥 第七章 软件测试（应用题必考！）
> **本章占应用题40分中的重要部分，必须熟练掌握白盒测试和黑盒测试的完整模板**

## 7.1 🔥 软件缺陷

```
错误（Error）→ 人为过失
    ↓
故障（Fault）→ 不正确的代码
    ↓
失效（Failure）→ 可观察到的错误行为
```

**例**：`result = i * i;`（本应是 i × 2）
- 调用 doubleValue(3) 返回 9 是 **Failure**
- 第3行的代码 `i * i` 是 **Fault**
- 程序员写错逻辑是 **Error**

## 7.2 ⭐ 软件测试定义

- **正向**：验证软件正常工作
- **逆向**：测试是为了发现错误而执行程序的过程
- **Myers观点**：好的测试用例很可能找到**迄今未发现**的错误

## 7.3 软件测试过程

```
计划（Plan）→ 准备（Prepare）→ 执行（Execute）→ 报告（Report）
```

## 7.4 ⭐ 软件测试阶段

```
单元测试 → 集成测试 → 系统测试 → 验收测试（α测试/β测试）→ 安装测试
```

| 阶段 | 测试对象 | 执行者 |
|:---|:---|:---|
| 单元测试 | 最小可测试单元（模块/类） | 开发人员 |
| 集成测试 | 模块间接口 | 开发/测试 |
| 系统测试 | 整个系统 | 测试团队 |
| 验收测试（α测试） | 内部人员模拟用户 | 内部 |
| 验收测试（β测试） | 典型用户实际使用 | 外部用户 |

## 7.5 ⭐ 测试原则

1. 所有测试应追溯到客户需求
2. 测试应尽早介入
3. **穷举测试是不可能的**
4. **Pareto原则**：80%的错误存在于20%的代码中
5. 测试应从"小规模"逐步转向"大规模"
6. **杀虫剂悖论**：重复使用相同用例将不再发现新缺陷，需不断增加新用例
7. 由独立的第三方承担测试更有效

#### ① 语句覆盖（最弱）

> **要求**：每个可执行语句**至少执行一次**

| 用例 | x= | y= | z= | 路径 | 覆盖情况 |
|:---|:---:|:---:|:---:|:---|:---|
| TC1 | **2** | **0** | **4** | a→b→c→d→e（abcde） | 语句段1 ✅，语句段2 ✅ |

- x=2 → 判定2中 (x=2) 为T，判定2为T，走d进入语句段2
- ✅ 所有可执行语句全部覆盖

#### ② 判定覆盖（分支覆盖）

> **要求**：每个判断的**真（T）和假（F）分支**至少各一次

| TC2 | **2** | **1** | **2** | F（y=1≠0） | T（x=2） | acde |

| 覆盖检查 | 判定1-T | 判定1-F | 判定2-T | 判定2-F |

| TC2 | | ✅ | ✅ | |

> **要求**：每个条件的所有可能取值组合至少出现一次
>

### （2）边界值分析

- 选取**正好等于、刚刚大于或刚刚小于**边界的值
- 基于**单故障假设**：每次只让一个变量取边界值

**以上题为例的边界值测试**：
- 年份边界：1990、1991、2048、2049
- 月份边界：01、02、11、12
- 长度边界：5位（少1）、6位（正确）、7位（多1）

## 🔥 常考易混对比

```
瀑布 vs 敏捷：预测性 vs 适应性
验证 vs 确认：做对 vs 做对的（Verification vs Validation）
功能性 vs 非功能性：做什么 vs 多好
包含(include) vs 扩展(extend)：必执行 vs 可选执行
聚合(◇) vs 组合(◆)：部分可独立 vs 不可独立
增量 vs 迭代：加功能 vs 完善功能
单元/集成/系统/验收测试：最小单元→接口→整体→最终
α测试 vs β测试：内部人员模拟 vs 典型用户试用
有效等价类 vs 无效等价类：合法 vs 非法（无效一次只测一个）
语句/判定/条件组合覆盖：最弱→中等→最强最常用
起始状态(●) vs 终止状态(◎)：必有且唯一 vs 可有可无/多个
同步消息 vs 异步消息：实心箭头(等待) vs 线形箭头(不等待)
```
