# 数据库高频面试题

> 后端岗数据库高频题，以 MySQL/InnoDB 为主要语境，按"索引 → 事务与锁 → 日志与架构 → SQL 优化"整理。

## 一、索引

### 1. B+ 树为什么适合做数据库索引？对比 B 树、哈希、跳表？

- 对比 B 树：B+ 非叶子节点不存数据（单页能放更多键，树更矮 IO 更少），叶子层链表便于范围扫描。
- 对比哈希：哈希不支持范围查询与排序，等值场景才占优（Memory 引擎）。
- 对比跳表：等查询复杂度下 B+ 树对磁盘块友好、扇出大层级低；Redis ZSet 用跳表是实现简单且内存可控。
- 高度估算：3 层 B+ 树可存约 2000 万行（16KB 页 × 1170 扇出 × 16 行）——所以千万级表走索引也只要 3 次 IO。

### 2. 聚簇索引和二级索引的区别？什么是回表？

- 聚簇索引（主键索引）：叶子存整行数据，InnoDB 表即索引组织表。
- 二级索引：叶子存"索引列 + 主键值"，命中后需拿主键回聚簇索引查整行 = **回表**。
- 优化：覆盖索引（查询列都在二级索引内，EXPLAIN 出现 Using index）避免回表；SELECT * 是回表大户。

### 3. 最左前缀原则是什么？联合索引怎么设计？

联合索引 (a,b,c) 相当于按 a 排序、a 相同再按 b……因此：

1. 查询条件必须从最左列开始连续命中才能走索引；
2. 范围查询后的列停止使用索引排序能力；
3. 设计口诀：等值列在前、排序列居中、范围列放最后；
4. ORDER BY 能否利用索引也遵循最左前缀 + 同序方向。

### 4. 索引失效的常见场景？

- 对索引列做函数/运算：`WHERE YEAR(create_time)=2026`；
- 隐式类型转换：字符串列用数字比较；
- 前导模糊 `LIKE '%xx'`（`'xx%'` 可以走）；
- OR 两侧有未加索引列；
- 优化器判断回表代价高于全表（区分度低的列，如性别）。

### 5. 什么是索引下推 ICP？

5.6+ 特性：联合索引 (name, age) 查询 `name LIKE '张%' AND age=20` 时，在**存储引擎层**先用索引中的 age 过滤再回表，减少回表次数。EXPLAIN 显示 Using index condition。

## 二、事务与锁

### 6. 事务四大特性的实现原理？

| 特性 | InnoDB 实现 |
|------|------|
| 原子性 | undo log 回滚 |
| 持久性 | redo log（WAL 先写日志） |
| 隔离性 | 锁 + MVCC |
| 一致性 | 以上三者共同保证的最终结果 |

### 7. MVCC 是什么？RC 和 RR 在 MVCC 上的差别？

每行隐藏字段 trx_id / roll_pointer 构成版本链，undo log 保存旧版本。读操作按 ReadView 判断可见性：

- RC：每次 SELECT 生成新 ReadView（能读到已提交的新版本）；
- RR：事务内第一次 SELECT 生成并复用同一 ReadView（保证可重复读）。
写仍加锁，读写互不阻塞是其核心价值。

### 8. 幻读是什么？InnoDB 怎么解决的？

同一事务两次范围查询返回不同行集合。RR 级别下：快照读靠 MVCC 规避；当前读（SELECT ... FOR UPDATE / UPDATE）靠**间隙锁 Next-Key Lock（记录锁+间隙锁）**锁住区间阻止插入。手动加 `FOR UPDATE` 即可防幻读。

### 9. 讲讲 InnoDB 的锁体系？

- 粒度：全局锁（备份 FTWRL）、表级锁/MDL 元数据锁、行级锁。
- 行锁三种形态：Record Lock（锁定索引记录）、Gap Lock（锁定开区间）、Next-Key Lock（前两者合集，左闭右开）。
- 关键规则：**行锁加在索引上**，无索引可用时升级为全表扫描逐行加锁 ≈ 锁全表——线上大事故高频根因。

### 10. 死锁怎么产生？如何排查与预防？

两个事务以不同顺序持有并等待对方锁。排查：`SHOW ENGINE INNODB STATUS` 看 LATEST DETECTED DEADLOCK。预防：

1. 多行更新按固定顺序（如按主键升序）；
2. 事务尽量短、避免在事务里做 RPC；
3. 合理索引缩小锁范围；
4. 小步提交，innodb_lock_wait_timeout 兜底。

### 11. 长事务有什么危害？

undo 无法清理导致版本链膨胀、MDL 锁阻塞 DDL、主从延迟放大、连接堆积。治理：监控 information_schema.innodb_trx，业务侧拆大事务，禁止在事务中 sleep/RPC。

## 三、日志与高可用架构

### 12. redo log 与 binlog 的区别？两阶段提交流程？

| 维度 | redo log | binlog |
|------|------|------|
| 层次 | InnoDB 引擎层 | Server 层 |
| 类型 | 物理日志（页修改） | 逻辑日志（语句/行） |
| 用途 | 崩溃恢复 | 主从复制、时间点恢复 |
| 写法 | 循环写 | 追加写 |

两阶段提交：redo prepare → 写 binlog → redo commit。保证两份日志一致，防止主从不一致或崩溃后丢数据。

### 13. 主从复制的原理与延迟优化？

主库写 binlog → 从库 IO 线程拉取写入 relay log → SQL 线程重放。延迟原因：大事务、从库单线程重放（并行复制可缓解）、从库机器弱、DDL。优化：ROW 格式 + 并行复制、拆分大事务、半同步复制保证不丢、读写分离时对一致性敏感的读强制走主库。

### 14. 分库分表怎么做？会引入什么问题？

垂直（按业务拆库/冷热分表）+ 水平（按 shard key 取模/_range）。引入问题：跨分片 join 与聚合、分布式事务、全局唯一 ID（雪花算法）、扩容数据迁移。原则：先索引与 SQL 优化，后读写分离，最后再考虑分片；shard key 尽量让高频查询单片命中。

## 四、SQL 优化实战

### 15. 慢查询怎么定位和优化？

定位：slow_query_log + long_query_time，或云平台慢日志分析。

分析四步法：

1. EXPLAIN 看执行计划：type 级别（ALL<index<range<ref<eq_ref<const>）、key 是否命中、rows 估算、Extra（Using filesort/temporary 是坏信号）；
2. 索引层面：补索引/改写满足最左前缀/建覆盖索引；
3. SQL 改写：深分页用游标 `WHERE id > ? LIMIT n`、join 小表驱动大表、避免 select *；
4. 结构层面：冗余字段、汇总表、缓存热数据。

### 16. count(*) 很慢怎么办？

InnoDB 无总行数存储（MVCC 下不同事务可见数不同）。方案：近似值 show table status；精确需求用计数表（事务内同更）或 Redis 计数 + 定期校准；二级索引 count 比聚簇索引小通常更快（优化器自动选择）。

### 17. 大表加字段/加索引怎么不停服？

MySQL 8.0 INSTANT ADD COLUMN 秒级；其他变更用 gh-ost / pt-online-schema-change：影子表 + 增量同步 + 原子 rename，控制拷贝限速降低主库压力。DDL 前 MDL 锁排队风险要避开高峰并在 session 设 lock_wait_timeout。

### 18. 为什么建议自增主键？

聚簇索引按主键有序插入，自增保证追加写、页满顺序分裂；若用随机 UUID 做主键会导致频繁页分裂、碎片化、缓冲池命中率下降。分布式下可用雪花 ID（趋势递增 + 全局唯一）兼顾两者。
