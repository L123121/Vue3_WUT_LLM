# RAG 系统实战笔记：从检索到生成

> 结合武理小精灵项目的实践经验，梳理 RAG（Retrieval-Augmented Generation）系统的核心链路、优化手段与踩坑记录。

## 一、RAG 整体架构

```
用户提问
  ↓
Embedding 模型 → 查询向量
  ↓
向量数据库检索（稠密 + 稀疏混合）
  ↓
重排（Reranker）→ 截断 → 组装上下文
  ↓
LLM 生成回答 + 引用来源
```

## 二、检索环节优化

### 1. 混合检索

- 稠密向量（如 BGE-small-zh）捕捉语义相似，稀疏向量（BM25/n-gram）捕捉关键词匹配，两者互补。
- 融合方式对比：加权融合（dense 0.6 + sparse 0.4）与 RRF（Reciprocal Rank Fusion）实测效果接近，加权更简单无需调参。

### 2. 父子段落架构

- 句子级向量化提高检索精度，命中后按父段落归并再注入上下文，上下文体积可降低 95%。
- 关键点：检索命中的是句子，进 LLM 的是完整父段落，保证信息完整。

### 3. 重排序（Rerank）

- 用 cross-encoder（如 BGE-reranker-base）对候选逐对打分，比双塔 embedding 分数更准。
- 自适应截断：断崖检测（分数差 > 0.05）+ 低分过滤（< 0.3）+ 硬上限，避免噪声段落挤占上下文。

## 三、生成环节优化

1. **上下文组装**：设置最大长度（如 6000 字），按文档阅读顺序二级排序，超长截断。
2. **引用来源**：回答附上 sources，用户可点击溯源，增强可信度。
3. **流式输出**：SSE 首包（检索完成事件）应 < 150ms，首 token 受 LLM 思考时间影响约 6s。

## 四、评测体系

| 指标 | 含义 |
|------|------|
| Recall | 相关文档被检索到的比例 |
| Precision | 检索结果中相关文档占比 |
| MRR | 第一个相关文档排名的倒数 |
| nDCG@5 | 前 5 结果按位置加权的质量 |

- 离线评测（检索指标）+ LLM-as-judge（答案质量）+ 人工抽检 + 线上反馈四层体系。
- 回归评估：指标变化超过 2% 触发告警。

## 五、踩坑记录

1. **MMR 去重误伤跨文档召回**：相似度 ≥ 0.85 直接剔除会把内容高度相似但不同文档的第二个相关文档整体剔掉，需限定为同文档内去重。
2. **RRF 排名单位**：必须按句子唯一 id 计 rank，不能按 docId，否则同一文档多条句子互相覆盖导致召回严重低估。
3. **扫描件 PDF**：pdf-parse 提取不到文本层，需 mupdf 渲染后走视觉模型 OCR。
4. **表格结构**：文本型 PDF 表格行列结构丢失，检测表格页后按页 OCR 重建 Markdown 表格。
5. **入库即清洗**：Prompt injection 行过滤 + 乱码占比闸门（warn/reject 双阈值）+ 内容 hash 去重，全部收敛在入库单一入口，保证 embedding 输入与进上下文文本一致。

## 六、Embedding 选型与 A/B

1. 本地 ONNX 推理（@huggingface/transformers）替代 API：零网络延迟、零调用成本，代价是首次加载 ~2s 与内存占用。
2. 升级模型（small→base）必须先离线 A/B：同语料同查询对比 Recall@5/MRR/nDCG@5，数据说话后再全量重建索引；维度变化意味着向量库必须重建。
3. 稀疏通道用 n-gram 哈希到整数 key（符合 SparseFloatVector 规范），字符串 key 会导致下游 NaN。
4. 向量缓存按"全文哈希 + 模型名"做 key——只截前 N 字符会让同前缀长文本错误命中同一缓存。

## 七、多路检索：改写 + 分解

- **Query 改写**解决多轮指代/省略（"它几点关门"），LLM 补全为自包含问题；改写结果与原文**双路并行检索合并去重**，reranker 统一重排兜住精度。
- **跨文档问题分解**解决"A 和 B 的区别"类问题 embedding 混合两实体语义：规则拆出实体级子查询并行检索扩召回池。核心约束：子查询只用于扩大召回，reranker 仍按用户原问题打分，语义偏移不影响精度。
- 改写异常检测：改写路候选数 < 原文的 0.3 倍时视为改写偏航，降级原文为主。

## 八、Agent 化：意图路由与工具调度

```
用户消息 → 意图路由（fastRoute 零成本关键词 / LLM 分类兜底）
   ├─ chat   纯 LLM（问候寒暄不触发检索）
   ├─ rag    检索管道（默认兜底）
   └─ agent  工具调度（search_knowledge_base / calculate）
```

- 有界多轮：maxToolRounds=2 + 无进展检测（连续同签名强制收尾）+ 收尾生成不带 tools，杜绝无限循环。
- 检索与生成分离：知识库工具走 retrieveOnly 只取证据，避免"决策 LLM + RAG 内部生成 + 收尾生成"三重调用的双重生成浪费。
- 失败降级：决策失败且未输出内容时自动回退 RAG 管道，而不是给用户一句误导性的道歉文案。

## 九、防幻觉：运行时引用校验

- 离线评测的 LLM-as-judge 管不了线上每一次回答，需要轻量 grounding 兜底：回答切句 → 逐句算与 RAG 上下文的字符 bigram 覆盖率 → coverage/level 分级标注。
- 设计取舍：只做标注不做阻断——bigram 衡量的是措辞来源，改写幅度大的正确答案可能被判 medium，阻断会误杀。
- 客套话/元话语过滤、代码块剥离是减少误报的关键细节。

## 十、评测驱动与坏例回流

1. 四层评测：离线检索指标（Recall/MRR/nDCG）→ RAGAS LLM-as-judge（独立 Key 防限流互抢）→ 人工抽检 → 线上 like/dislike。
2. 回归基线：指标波动 > 2% 告警；任何检索链路改动（融合方式/去重策略/阈值）必须带同口径 A/B 数据。
3. **坏例闭环**：dislike 反馈自动导出为待标注数据集条目 → 人工补 relevant_doc_ids → 并入回归集。静态测试集会老化，线上反馈才是测试集的生长点。

## 十一、性能工程要点

| 手段 | 效果 |
|------|------|
| 多级缓存（检索结果/query 改写/rerank） | 重复问题秒回，TTL 平衡新鲜度 |
| SSE 流式 + 事件分阶段下发 | retrieval 事件首包 ~130ms，用户先看到"正在检索" |
| 客户端断开 abort 传播 | 取消信号贯穿 Agent→工具→底层检索，不白烧 GPU/API |
| 批量 upsert + 重试 | 大文档重建抗瞬时断连 |
