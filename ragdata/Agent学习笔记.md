### 第一章：初识智能体

#### 一、智能体的定义

智能体 = 能通过**传感器**感知**环境**，**自主**地通过**执行器**采取**行动**以达成目标的实体。

| 要素 | 说明 | 旅行助手示例 |
|------|------|-------------|
| **环境** | 外部世界 | 互联网、天气系统、票务平台 |
| **传感器** | 感知环境的能力 | 用户输入、API 返回数据 |
| **执行器** | 影响环境的手段 | API 调用、搜索工具、预订系统 |
| **自主性** | 独立决策，非被动响应 | 核心特征 |

#### 二、传统智能体演进

```
简单反射 → 基于模型 → 基于目标 → 基于效用 → 学习型
（恒温器） （有记忆）  （能规划）  （会权衡）  （自我进化）
```

| 阶段 | 核心能力 | 回答的问题 | 典型例子 |
|------|----------|-----------|----------|
| **简单反射** | 条件-动作规则，无记忆 | "当前输入该怎么反应？" | 自动恒温器 |
| **基于模型** | 内部世界模型，有记忆 | "世界现在是什么样子？" | 隧道中的自动驾驶车 |
| **基于目标** | 前瞻性规划 | "做什么才能达成目标？" | GPS 导航（A* 算法） |
| **基于效用** | 效用值权衡多目标 | "哪种行为最满意？" | 投资决策系统 |
| **学习型** | 通过环境互动自主学习 | "如何改进策略？" | AlphaGo Zero |

#### 三、LLM 驱动的新范式

| 维度 | 传统智能体 | LLM 智能体 |
|------|-----------|-----------|
| **能力来源** | 工程师显式编程 | 海量数据预训练 + 涌现能力 |
| **行为边界** | 确定、有界 | 灵活、通用 |
| **核心转变** | 编写代码 | 引导通用"大脑"规划、行动、学习 |

**LLM 智能体新特性**：
- **规划与推理**：将高层目标分解为逻辑子任务
- **工具使用**：主动识别信息缺口，调用外部工具
- **动态修正**：将反馈视为新约束，调整行动

#### 四、三大分类维度

**按内部决策架构**：简单反射 → 模型式 → 目标式 → 效用式 → 学习型

**按时间与反应性**：

| 类型 | 特点 | 优势 | 劣势 | 适用场景 |
|------|------|------|------|----------|
| **反应式** | 即时响应，无规划 | 速度快、开销低 | 短视、局部最优 | 安全气囊、高频交易 |
| **规划式** | 深思熟虑再行动 | 战略性、有远见 | 时间和计算成本高 | 棋手、路径规划 |
| **混合式** | 底层反应 + 高层规划 | 兼顾速度和远见 | 架构复杂 | 现代 LLM Agent |

**按知识表示**：

| 范式 | 核心信念 | 优势 | 劣势 | 类比 |
|------|----------|------|------|------|
| **符号主义** | 智能源于符号逻辑操作 | 透明可解释 | 脆弱、知识获取瓶颈 | 一丝不苟的图书管理员 |
| **亚符号主义** | 知识是神经网络中的统计模式 | 强大模式识别 | 黑箱、可能幻觉 | 牙牙学语的孩童 |
| **神经符号主义** | 融合两者优点 | 既能学习又能推理 | 架构复杂 | 卡尼曼系统1+系统2 |

> LLM Agent 是神经符号主义的最佳实践：内核是神经网络（模式识别），工作时生成结构化中间步骤（符号推理）。

#### 五、Agent Loop（智能体循环）

```
感知（Perception）→ 思考（Thought）→ 行动（Action）→ 观察反馈（Observation）
     ↑                                                          |
     └──────────────────────────────────────────────────────────┘
```

| 阶段 | 做什么 |
|------|--------|
| **感知** | 通过传感器接收环境输入（用户指令或上一步反馈） |
| **思考** | LLM 驱动的内部推理：规划（分解子任务）+ 工具选择 |
| **行动** | 通过执行器执行具体操作（调用工具） |
| **观察** | 环境返回结果，作为下一轮循环的输入 |

#### 六、TAO 范式（Thought-Action-Observation）

LLM 智能体的标准化交互协议：

| 组件 | 形式 | 作用 |
|------|------|------|
| **Thought** | 自然语言 | 分析情境、反思、分解问题、规划行动 |
| **Action** | 函数调用 | 具体操作（工具名 + 参数） |
| **Observation** | 自然语言 | 环境返回的结果反馈 |

#### 七、PEAS 模型（任务环境描述）

| 要素 | 含义 | 旅行助手示例 |
|------|------|-------------|
| **P**erformance | 成功标准 | 旅行方案满意度、成本效益 |
| **E**nvironment | 外部世界 | 互联网、天气系统、票务平台 |
| **A**ctuators | 影响手段 | API 调用、搜索工具、预订系统 |
| **S**ensors | 感知方式 | 用户输入、API 返回数据 |

**数字环境特性**：部分可观察、可能随机、多智能体、序贯（当前影响未来）、动态变化。

#### 八、Workflow vs Agent

| 维度 | Workflow | Agent |
|------|----------|-------|
| **核心逻辑** | 预定义的结构化编排 | 目标驱动的自主决策 |
| **决策方式** | 静态流程图，if-then 规则 | 基于实时信息动态推理 |
| **灵活性** | 按部就班执行指令 | 自主达成目标 |
| **典型场景** | 费用报销审批 | 智能旅行助手 |

### 第二章：智能体发展史

#### 一、符号主义时代（1950s-1970s）

**理论基础**：物理符号系统假说（PSSH，1976）— 智能的本质就是符号的计算与处理。

**关键里程碑**：

| 时期 | 里程碑 | 核心贡献 |
|------|--------|----------|
| 1966 | **ELIZA** | 基于规则的自然语言对话，揭示"ELIZA效应" |
| 1968-1970 | **SHRDLU** | 多 AI 模块集成，奠定"感知-思考-行动"闭环 |
| 1970s | **MYCIN** | 专家系统在医疗领域的成功，600 条 IF-THEN 规则 |
| 1976 | **PSSH** | 纽厄尔与西蒙的理论奠基 |

**专家系统三大组件**：知识库（IF-THEN 规则）+ 推理机（正向链/反向链）+ 用户界面

**符号主义的根本挑战**：
- **知识层面**：知识获取瓶颈、常识问题（Cyc 项目数十年成果有限）
- **逻辑层面**：框架问题、系统脆弱性

#### 二、联结主义复兴（1980s）

从手动编码知识到创造能自主学习的系统。核心特征：
- 知识的分布式表示（连接权重）
- 通过反向传播算法调整权重
- 强大的感知和模式识别能力

#### 三、强化学习（交互式决策学习）

**核心框架**：Agent + Environment + State + Action + Reward

**工作循环**：观察状态 → 选择行动 → 环境转移 → 获得奖励 → 更新策略

**里程碑**：AlphaGo Zero — 通过强化学习发现超越人类的围棋策略。

#### 四、预训练范式（大规模知识获取）

**两阶段**：预训练（海量语料自监督学习）→ 微调（少量标注数据适配任务）

**涌现能力**（模型规模跨越阈值后出现）：
- **上下文学习**：Few-shot/Zero-shot 完成新任务
- **思维链推理**：逐步输出推理过程

**关键转变**：预训练以全新方式解决了符号主义时代最棘手的"知识获取瓶颈"。

#### 五、LLM 驱动的现代智能体（2020s）

三大流派深度融合：
- **符号主义**：提供逻辑推理框架
- **联结主义**：提供感知与模式识别
- **行为主义**：提供从经验中学习决策的能力
- **LLM** 成为执行符号推理、工具调用和规划决策的核心"大脑"

### 第三章：大语言模型基础

#### 一、从 N-gram 到 Transformer

**N-gram 模型**：基于马尔可夫假设，数据稀疏、泛化差。

**词嵌入**（Bengio, 2003）：连续向量表示，语义相似的词在向量空间中距离近。经典类比：King - Man + Woman ≈ Queen。

**RNN → LSTM**：隐藏状态作为短期记忆，LSTM 通过门控机制解决长期依赖问题。

**Transformer**（Vaswani, 2017）：完全抛弃循环，仅依赖注意力机制实现并行计算。

#### 二、Transformer 核心机制

**自注意力（Self-Attention）**：

```
Attention(Q,K,V) = softmax(QK^T / √d_k) × V
```

每个 Token 产生 Query、Key、Value 三个向量。注意力分数 = Q 和 K 的点积 → 缩放 → softmax → 加权求和 V。

**多头注意力**：将 Q、K、V 分成 h 个头独立计算，拼接后线性变换。让模型同时捕捉多种关系类型。

**位置编码**：用 sin/cos 函数为 Token 添加位置信息（自注意力本身没有顺序概念）。

**Decoder-Only 架构**（GPT 系列）：移除编码器，只保留解码器。核心洞察：语言的根本任务是预测下一个最可能的 Token。

**掩码自注意力**：防止模型看到未来的 Token，确保预测只依赖前面的上下文。

#### 三、提示工程

**采样参数**：
- **Temperature**：低（0-0.3）确定精确，中（0.3-0.7）平衡，高（0.7-2）创意多样
- **Top-k**：只保留概率最高的 k 个 Token
- **Top-p（核采样）**：保留累积概率 ≥ p 的最小 Token 集合

**提示策略**：
- **Zero-shot**：无示例，依赖预训练泛化
- **One-shot**：一个示例展示格式
- **Few-shot**：多个示例帮助理解任务边界
- **CoT（思维链）**："think step by step" 激发显式推理链

**指令微调**：在"指令-响应"数据上微调，将文本补全模型变为指令跟随模型。

#### 四、文本分词

**子词分词**（现代 LLM 使用）：常见词保留为整体，罕见词拆分为有意义的子片段。

| 分词方法 | 使用模型 | 特点 |
|----------|----------|------|
| **BPE** | GPT 系列 | 迭代合并最高频相邻 Token 对 |
| **WordPiece** | BERT | 合并使语言模型似然最大化的对 |
| **SentencePiece** | Llama | 将空格视为普通字符，语言无关 |

#### 五、缩放定律与局限性

**Chinchilla 定律**（DeepMind, 2022）：最优模型比之前认为的更小，但需要更多训练数据。

**幻觉（Hallucination）**：模型输出与事实、用户输入或上下文矛盾。

| 类型 | 说明 |
|------|------|
| **事实幻觉** | 与现实矛盾 |
| **忠实幻觉** | 未忠实反映源材料 |
| **内在幻觉** | 直接与输入矛盾 |

**缓解策略**：
- **数据层**：高质量清洗、知识注入、RLHF
- **模型层**：新架构、不确定性表达
- **推理层**：RAG、多步推理验证、外部工具调用

### 第四章：三大经典范式 ⭐⭐⭐

#### 4.1 ReAct（推理 + 行动）

**核心**：Thought → Action → Observation 交替循环

```
问题 → Thought（分析）→ Action（调用工具）→ Observation（结果）→ Thought → ... → Finish
```

**适用场景**：需要外部知识、精确计算、API 交互的任务

**实现要点**：
- 工具三要素：Name + Description + Execution Logic
- 系统提示词定义角色、可用工具列表、严格输出格式
- 正则表达式解析 Thought 和 Action
- max_steps 防止无限循环

**优势**：高可解释性、动态规划和纠错、工具协同

**局限**：强依赖 LLM 能力、多次串行调用效率低、Prompt 脆弱、可能局部最优

#### 4.2 Plan-and-Solve（先规划后执行）

**核心**：先生成完整计划，再逐步执行

```
问题 → Planner（生成步骤列表）→ Executor（逐步执行，带上下文）→ 最终答案
```

**适用场景**：结构化可分解的任务（多步数学、报告编写、代码生成）

**实现要点**：
- Planner 输出 Python 列表格式的步骤
- Executor 每步接收：原始问题 + 完整计划 + 历史结果 + 当前步骤
- 使用 `ast.literal_eval` 安全解析计划

**优势**：稳定性强、结构清晰、全局规划

#### 4.3 Reflection（反思迭代）

**核心**：执行 → 反思 → 优化，可多轮迭代

```
任务 → 初始执行 → 反思（找问题）→ 优化 → 反思 → ... → 无需改进 → 输出
```

**适用场景**：高质量要求的场景（关键代码、科学推理、决策支持）

**实现要点**：
- Memory 模块存储执行和反思记录
- 三个提示模板：初始执行、反思（严格代码审查）、优化
- 终止条件：反思结果包含"无需改进"

**优势**：质量从"能用"跃升到"最优"、自纠错

**局限**：至少多 2 次 LLM 调用、延迟显著增加

#### 三种范式对比

| 范式 | 策略 | 思维风格 | 核心优势 | 最佳场景 |
|------|------|----------|----------|----------|
| **ReAct** | 思考-行动-观察循环 | 逐步反应式 | 适应性与动态纠错 | 探索、工具依赖任务 |
| **Plan-and-Solve** | 先规划后执行 | 结构化顺序式 | 稳定性与结构性 | 确定性多步推理 |
| **Reflection** | 执行-反思-迭代 | 自我批判式 | 质量提升 | 精度要求高的输出 |

> **三者可组合**：Plan-and-Solve 每步内用 ReAct，外层用 Reflection 包裹保证质量。

### 第五章：低代码平台

#### 三个平台对比

| 维度 | Coze（扣子） | Dify | n8n |
|------|-------------|------|-----|
| **定位** | 零代码 Agent 构建平台 | 开源 LLM 应用开发平台 | 开源工作流自动化工具 |

- 快速原型验证、非技术用户 → **Coze**

**核心价值**："混合开发"思维 — 用低代码平台快速验证想法，用代码实现精细化控制。

### 第六章：框架开发实践

#### 四大框架对比

| 维度 | AutoGen | AgentScope | CAMEL | LangGraph |
|------|---------|------------|-------|-----------|
| **核心哲学** | 对话驱动协作 | 工程优先多智能体平台 | 角色扮演自主合作 | 状态机有向图 |
| **协作模型** | 群聊 + 定义角色 | 消息驱动 + MsgHub | 双智能体 Inception Prompting | 节点和边 + 条件路由 |
| **控制风格** | 半结构化（轮询或自定义） | 消息中心 + Pipeline 编排 | 涌现式（初始提示驱动） | 显式图（状态、节点、边） |
| **最佳场景** | 多角色对话工作流 | 大规模高可靠分布式系统 | 深度创意双智能体协作 | 迭代、可审计工作流 |

**核心权衡**："涌现协作"（AutoGen、CAMEL）vs "显式控制"（LangGraph）。

**AutoGen**：
- AssistantAgent（任务解决）+ UserProxyAgent（用户代表 + 执行器）
- RoundRobinGroupChat 顺序对话协调
- 异步优先设计，支持 DeepSeek 等非 OpenAI 模型

**AgentScope**：
- 消息驱动架构：所有交互抽象为消息发送/接收
- MsgHub：灵活路由（点对点、广播、多播）+ 消息持久化 + 原生分布式支持
- 结构化输出：Pydantic 模型约束智能体行为

**CAMEL**：
- "轻架构，重提示" — 高质量初始提示带来高质量协作
- Inception Prompting：结构化初始指令（角色定义 + 目标 + 行为约束）
- 适合深度创意协作，不适合严格流程控制

**LangGraph**：
- 三要素：State（共享状态 TypedDict）+ Node（Python 函数）+ Edge（连接 + 条件路由）
- 原生循环支持：条件边实现"反思-纠错"循环
- 高可控性和可预测性，适合生产级可审计应用

### 第七章：从零构建 Agent 框架

#### 四大设计理念

1. **轻量级与教学友好**：核心代码按章节组织，不引入重型依赖
2. **基于标准 API**：在 OpenAI 兼容接口之上构建
3. **渐进式学习路径**：每章保存为可 pip 安装的历史版本
4. **万物皆为工具**：Memory、RAG、MCP 等模块统一抽象为工具

#### 架构分层

```
核心框架层（core/）：agent.py、llm.py、message.py、config.py
Agent 实现层（agents/）：simple_agent.py、react_agent.py、reflection_agent.py、plan_solve_agent.py
工具系统层（tools/）：base.py、registry.py、chain.py、async_executor.py、builtin/
```

#### 五种 Agent 范式

| 范式 | 特点 |
|------|------|
| **SimpleAgent** | 最基础对话，支持可选工具调用 |
| **ReActAgent** | 推理与行动结合 |
| **ReflectionAgent** | 自我反思与迭代优化 |
| **PlanAndSolveAgent** | 分解规划与逐步执行 |
| **FunctionCallAgent** | 基于 OpenAI 原生函数调用机制（更鲁棒） |

#### 工具系统

**Tool 基类**：name + description + run(parameters) + get_parameters()

**ToolRegistry**：工具注册中心，支持 Tool 对象注册和函数直接注册

**高级特性**：
- **ToolChain**：多工具顺序执行，步骤间通过模板变量传递数据
- **AsyncToolExecutor**：基于 ThreadPoolExecutor 并行工具执行

---

### 第八章：记忆与检索

#### 四层记忆架构

| 层级 | 组件 | 说明 |
|------|------|------|
| **基础设施层** | MemoryManager、MemoryItem、MemoryConfig | 统一协调 |
| **记忆类型层** | Working、Episodic、Semantic、Perceptual | 四种记忆 |
| **存储后端层** | Qdrant（向量）、Neo4j（图）、SQLite（文档） | 多存储 |
| **嵌入服务层** | DashScope / sentence-transformers / TF-IDF | 三级降级 |

#### 四种记忆类型

| 类型 | 用途 | 存储 | 关键设计 |
|------|------|------|----------|
| **Working（工作记忆）** | 当前会话上下文 | 内存 + TTL | 上限 50 条，默认 60 分钟过期 |
| **Episodic（情景记忆）** | 具体事件/经历 | SQLite + Qdrant | 按会话索引，时间序列检索 |
| **Semantic（语义记忆）** | 抽象知识/规则 | Qdrant + Neo4j | 实体/关系抽取，知识图谱 |
| **Perceptual（感知记忆）** | 多模态数据 | 按模态 Qdrant 集合 | CLIP（图像）、CLAP（音频） |

#### 记忆评分公式

- **工作记忆**：TF-IDF 相似度（0.7）+ 关键词匹配（0.3），乘以时间衰减和重要性权重
- **情景记忆**：(向量分数 × 0.8 + 时效性 × 0.2) × 重要性权重
- **语义记忆**：(向量分数 × 0.7 + 图谱分数 × 0.3) × 重要性权重
- **时间衰减**：`exp(-0.1 × hours/24)`，下限 0.1

#### 记忆工具操作

add（存储）→ search（检索）→ forget（遗忘，三种策略）→ consolidate（晋升：工作→情景→语义）

#### RAG 系统设计

**"五层七步"架构**：用户层 → 应用层 → 处理层 → 存储层 → 基础层

**处理流水线**：任意格式 → MarkItDown → Markdown → 智能分块 → 向量化 → Qdrant 存储

**高级检索策略**：
- **MQE（多查询扩展）**：LLM 生成 N 个语义等价查询变体，合并搜索结果
- **HyDE（假设文档嵌入）**：生成假设答案段落，用其嵌入作为搜索查询

### 第九章：上下文工程

#### 核心概念

上下文工程 = 提示工程的进化。不仅关注指令，还优化进入模型上下文窗口的**整个 Token 集**。

**上下文腐烂（Context Rot）**：Token 数增加，模型回忆和推理能力下降。原因是 Transformer 的 O(n²) 复杂度。

**核心洞察**："上下文必须被视作一种有限资源，且具有边际收益递减。"

#### GSSC 流水线（ContextBuilder）

| 阶段 | 做什么 |
|------|--------|
| **Gather（收集）** | 从多源收集候选信息（系统指令、记忆、RAG、对话历史） |
| **Select（选择）** | 组合评分：`relevance × 0.7 + recency × 0.3`，贪心算法填充 Token 预算 |
| **Structure（结构化）** | 固定架构模板：[角色策略] [任务] [证据] [上下文] [输出] |
| **Compress（压缩）** | 分区感知截断，保持结构完整性 |

#### 长时任务管理策略

| 策略 | 说明 |
|------|------|
| **Compaction（压缩）** | 接近 Token 限制时生成高保真摘要，用新窗口重启 |
| **Structured Note-Taking（结构化笔记）** | 定期将关键信息写入持久存储，按需拉回 |
| **Sub-Agent Architecture（子智能体架构）** | 主智能体规划，子智能体在干净窗口中深入探索，返回浓缩摘要 |

#### 工具设计

**NoteTool**：结构化外部记忆，每个笔记是独立 `.md` 文件 + YAML front matter。七种操作：create、read、update、search、list、summary、delete。

**TerminalTool**：安全文件系统访问，四层安全架构：命令白名单 + 沙箱 + 超时控制 + 输出大小限制。

### 第十章：智能体通信协议 ⭐⭐⭐

#### 为什么需要协议？

单体智能体三大限制：工具集成困境、能力扩展瓶颈、协作缺失。

#### 三种协议对比

| 维度 | MCP | A2A | ANP |
|------|-----|-----|-----|
| **提出者** | Anthropic | Google | 开源社区 |
| **定位** | 智能体与工具的桥梁 | 智能体间的对话 | 智能体的"互联网" |
| **核心理念** | 上下文共享 | 对等通信 | 去中心化服务发现 |
| **通信模式** | Client-Server | 点对点 P2P | 网络拓扑 |
| **核心概念** | Tools/Resources/Prompts | Task/Artifact | Service/Discovery/Routing |
| **适用规模** | 单智能体能力增强 | 小规模紧密协作 | 大规模开放网络 |
| **成熟度** | 生态相对成熟 | Sample Code 阶段 | 概念性框架 |

#### MCP 详解

**类比**：MCP = USB-C，统一智能体与外部工具的交互方式。

**三层架构**：Host（宿主）→ Client（客户端）→ Server（服务器）

**三大能力**：Tools（执行操作）、Resources（提供数据）、Prompts（提供模板）

**五种传输方式**：Memory、Stdio、Stdio with Args、HTTP/SSE、StreamableHTTP

**MCP vs Function Calling**：FC 是模型能力（学会打电话），MCP 是基础设施协议（全球电话标准）。互补关系。

#### A2A 详解

P2P 网状拓扑，核心概念：Task（标准化生命周期）+ Artifact（任务产出物）。支持任务协商。

#### ANP 详解

大规模智能体网络基础设施。核心机制：DID 身份验证 + 服务注册/发现/路由。

### 第十一章：Agentic RL

#### 训练流水线

```
预训练（下一个 Token 预测）→ 后训练：SFT → 奖励建模 → RL 微调
```

#### SFT（监督微调）

用（prompt, completion）对教模型任务格式和基本推理模式。提供 RL 的可行起点。

**LoRA（低秩适应）**：将权重更新分解为低秩矩阵 ΔW = BA，参数量减少 256 倍。

#### GRPO（群组相对策略优化）

PPO 的简化变体，消除 Value Model 需求。

**核心思想**：每个问题采样多个答案，用群组均值归一化奖励。

**PPO vs GRPO**：PPO 需要 4 个模型（策略、参考、价值、奖励），GRPO 只需 2 个（策略、参考）。

**GRPO 流程**：采样 → 奖励计算 → 相对奖励（减群组均值）→ 策略更新（带 KL 惩罚）

**三种奖励函数**：
- **准确性奖励**：正确 1，错误 0
- **长度惩罚**：正确答案过长时扣分
- **步骤奖励**：正确答案有推理步骤时加分

### 第十二章：智能体性能评估

#### 三大评估基准

| 基准 | 评估内容 | 核心指标 |
|------|----------|----------|
| **BFCL** | 函数调用能力（Simple/Multiple/Parallel/Irrelevance） | AST 匹配准确率 |
| **GAIA** | 真实世界任务综合表现（466 问题，3 级难度） | 准精确匹配率 |
| **数据生成质量** | 生成数据的质量（AIME 案例） | LLM Judge + Win Rate + 人工验证 |

**BFCL（伯克利函数调用排行榜）**：AST 匹配算法比较语法树结构，支持忽略参数顺序、识别等价表达式。

**GAIA（通用 AI 助手）**：Level 1（零步推理）→ Level 2（1-3 步）→ Level 3（>3 步）。答案必须以 "FINAL ANSWER:" 格式给出。

**其他评估基准**：ToolBench、API-Bank、AgentBench、WebArena、ChatEval、SOTOPIA。

### 第十五章：赛博小镇

#### 核心理念

将 LLM 与游戏引擎结合，构建拥有真正"智能"NPC 的虚拟办公室。NPC 能理解自然语言、记住互动历史、根据好感度调整行为。

#### 五大核心功能

1. **智能 NPC 对话系统** — 基于角色设定和记忆的自然语言对话
2. **记忆系统** — 短期 + 长期记忆，保留互动历史
3. **好感度系统** — 从陌生到挚友的五级关系变化
4. **游戏化交互** — 2D 像素风格办公室场景
5. **实时日志系统** — 所有对话和互动记录

#### 技术架构

前端（Godot 4.5）→ 后端（FastAPI）→ 智能体层（HelloAgents）→ 外部服务（LLM + Qdrant + SQLite）

#### NPC 智能体系统

每个 NPC 是独立 SimpleAgent 实例：
- 独特系统提示词定义身份和性格
- WorkingMemory（短期，10 条，120 分钟）
- EpisodicMemory（长期，SQLite + Qdrant 向量检索）

**三个 NPC**：张三（Python 工程师）、李四（产品经理）、王五（UI 设计师）

#### 好感度系统

| 等级 | 分数 | 行为表现 |
|------|------|----------|
| 陌生 | 0-20 | 礼貌但疏远，回复简短 |
| 熟悉 | 21-40 | 愿意简单交流 |
| 友好 | 41-60 | 当作朋友，回复详细 |
| 亲密 | 61-80 | 非常信任，分享私人话题 |
| 挚友 | 81-100 | 无话不谈 |

通过**动态调整系统提示词**实现：不同好感度等级对应不同提示词指令。

#### 批量对话生成（轻负载模式）

- **批量生成**：后台每 5 分钟更新 NPC "背景对话"
- **即时响应**：玩家交互时调用专属 Agent 生成个性化回复
- 成本降至 1/3，NPC 始终"活着"

#### Godot 游戏实现

- 玩家 WASD 移动，靠近 NPC 按 E 触发对话
- NPC 随机巡逻，交互时停止巡逻
- API 客户端用 3 个独立 HTTPRequest 节点实现异步通信
- 每 30 秒定时获取 NPC 状态更新对话气泡
